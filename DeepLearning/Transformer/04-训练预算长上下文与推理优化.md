## 1. 训练预算的单位

epoch 取决于数据规模，step 取决于批量，token 数取决于长度。比较语言模型时应说明有效训练 token、全局批量、学习率调度与总计算，而非只说训练了多少轮。序列打包和梯度累积改变更新与利用率。

假设每次优化器更新消耗全局 128 条、平均 512 个有效 token，则一万次更新约看 6.55 亿 token；padding 不计入有效目标，序列打包可能显著改变利用率。梯度累积改变微批到更新的关系，学习率调度应与选定进度单位一致。

比较训练时分别记录有效 token、总更新、模型规模与端到端时间；同样 token 下不同架构仍可能花费不同计算。不要把更短文本数据上的相同 epoch 解释为同预算。超参数搜索及失败运行若用于比较，也应说明是否计入总资源成本。

<a id="sec-2"></a>

## 2. 推理过程

前缀预填充与逐 token 解码具有不同成本。KV cache 减少历史重复，批量处理提高吞吐但可能增加延迟。量化、优化注意力与缓存管理都需验证输出质量及实际硬件收益。

<a id="sec-1-1"></a>

### 基础算例：首 token 延迟与持续生成速度分开测

两个系统生成 100 个 token 总耗时相同，一个预填充很快但后续慢，另一个预填充慢但解码快，交互感受可能不同。应分别记录首 token 延迟、解码每 token 时间、总时间和并发吞吐。固定提示与输出长度、精度和硬件后再比较；否则缓存命中、批量或长度差异会被误认为算法优化。上下文能被输入不等于模型有效利用远处证据，后者需要任务测试。

<a id="sec-2-1"></a>

### 机制展开：吞吐与交互延迟不是同一个最优目标

更大并发批量可能提高单位时间 token 数，却增加单请求等待；缓存和调度还影响首 token 与后续 token 延迟。基准应固定输入输出长度、硬件、精度和是否预热，分别报告相应指标。只比较一个平均时间会掩盖长尾和阶段差异；优化策略是否合适，要回到离线批处理或交互服务的具体需求。

<a id="deep-dive-2"></a>

### 深入讲解：训练和推理优化需要用相同质量目标比较资源

训练预算至少包含有效token、优化器更新、全局批、模型规模和时间。padding不算同等监督信息，打包与累积改变利用率和更新关系；同epoch或同step并不必然同计算。

推理prefill常能批量复用权重，decode还需读取历史KV。量化、缓存、批处理和并发针对不同成本，大批可能提高总吞吐却增加排队，不能用一个tokens/s代表所有用户体验。

长上下文测试固定问题与证据，改变位置、干扰、文档数和冲突。输入未报错只说明接口接受；证据被截断与证据在场却没用，是不同失败，应分别定位。

每项优化同时检查输出与资源。精度变化可能影响概率和长输出，缓存策略可能改变位置，截断直接改变可见信息；需要固定回归样例和独立任务。

报告达到某质量所需成本，或固定成本下质量，两者问题不同。优化必须说明保留了什么功能、改变了哪些条件，才能判断是否适合实际负载。

<a id="sec-3"></a>

## 3. 长度外推

长上下文需要考虑位置机制、训练分布、证据位置、干扰与成本。能够接收长输入不保证有效利用全部内容。测试应改变答案所在位置、文档数量与冲突信息，观察任务表现而非只确认没有报错。

构造受控长文本时固定问题与关键证据，分别把证据放在开头、中间和末尾，再逐步增加无关段落与相似干扰。另测多个分散片段需要联合推理的题目，区分“找到一个显眼词”与真正整合长距离信息。若含冲突版本，题目应明确采用哪份及其时间。

每个长度报告任务正确率、可用证据召回、延迟和峰值内存；对比短上下文时保持解码和回答预算一致。输入能装下但答案证据被截断，属于前处理失败；证据存在却未被使用，才是利用能力问题。位置缩放或上下文扩展改变后还要回归短文本，检查原能力是否退化。

<a id="sec-4"></a>

## 4. 预填充与解码为什么不同

预填充一次处理已有整段前缀，可并行利用矩阵运算；逐 token 解码每次只有少量新查询，需要不断读缓存，常更受内存带宽和调度影响。相同设备上，两阶段最优批量与瓶颈不同，因此报告首 token 延迟和后续生成速度更有解释性。

训练预算也应按有效 token 而非只按填充后长度计算。大量 padding 会消耗计算却没有同样监督，序列打包提高利用率时，还要明确文档边界与可见性。吞吐提高不等于看到了更多独立内容。

长度外推可用多证据问题、冲突版本和不同位置测试。若短输入正确长输入失败，可能是检索、位置、干扰或上下文组织，不应仅归因某一种位置编码。逐项对照才能选择压缩、检索或结构方案。

<a id="sec-5"></a>

## 5. 综合算例与实现核对

给定同一提示，分别统计输入预填充时间、首 token 时间和后续每 token 时间。长输入会增加预填充与缓存，长输出则增加串行解码步骤。这两个长度对用户等待和系统吞吐有不同作用。

优化批处理时还需考虑请求长度不同。短请求若等待长请求组批，平均吞吐可能提高但交互延迟更差。对服务型任务，应按实际请求分布测量，不只用固定长序列跑峰值。

量化后核对输出或任务指标，缓存优化后与无缓存相同设置比较。每项加速都要说明是等价实现、数值近似还是模型结构改变，读者才能理解性能收益与质量风险。

<a id="sec-6"></a>

## 6. 进阶：推理成本分解与研究报告

标准预填充注意力含序列平方关系，逐 token 解码借助缓存仍需读取历史键值；两阶段的算力与带宽瓶颈不同。首 token 延迟、后续速度、批量吞吐和峰值内存应分开报告。

量化、共享键值头、稀疏与内核融合改变的层次不同：数值近似、结构或执行方式需明确。比较长上下文能力还要改变证据位置和冲突干扰，而非只验证能接收某长度或展示一个成功提示。

<a id="sec-6-1"></a>

### 长上下文推理应按阶段与资源比较

预填充同时处理提示并建立缓存，解码阶段每次生成少量新 token；两者的计算并行度、内存访问和延迟构成不同。报告首 token 延迟、后续每 token 延迟与总吞吐，比一个平均耗时更能描述实际体验。

上下文变长时，缓存占用增加，批量并发能力可能下降。量化、KV 头共享、分块和缓存调度分别改变精度、结构或资源管理，不能只用“支持更长”推断成本可接受。应固定硬件、精度、批量、输入输出长度和测量方法。

长度外推还包含统计问题：模型是否能使用远距离证据、位置表示是否超出训练范围、任务是否本来需要全部上下文。可把关键证据放在不同位置并加入干扰，测量准确率随距离与长度的变化，区分接口容量和有效利用能力。

<a id="sec-7"></a>

## 7. 练习与解析

**题目：** 模型支持 64k 输入，是否意味着任意 64k 文本问答都可靠？

**解析：** 不是，窗口是接口和资源边界，可靠性仍取决于信息检索、表示与任务训练。应按具体任务、位置和长度分组评估。

<a id="sec-8-2"></a>

### 边界追问：平均每 token 时间能否代表交互体验

**问题：** 两系统总耗时相同，但首 token 等待差很多，能否称延迟等价？

**推理解析：** 不能，预填充、排队、持续解码和尾部延迟不同。按需求分别报告首 token、后续速度、并发吞吐及长尾，固定长度与硬件。一次性缓存和预热成本是否包含也要说明，不能把不同测量对象拼成统一速度结论。

<a id="sec-8"></a>

## 8. 进阶研究练习与解析

**问题：** 验证带 KV cache 的解码与每步重算完整前缀是否等价，需要固定什么？

**解析：** 固定模型评估模式、位置索引、掩码、前缀与数值容差，逐步比较下一 token logits。历史表示需在扩展前缀时不变，这是因果结构的关键；双向编码器不能简单用同样缓存假设。

**反例：** 修改已有前缀、重置位置或切换滑窗策略后仍沿用旧缓存，会破坏等价。质量和速度应分别测量，报告预填充、逐步解码与缓存内存，不把同一正确率下的全部成本汇成模糊“更快”。

<a id="sec-8-1"></a>

### 综合练习：长上下文能力与接口容量分开验收

**问题：** 模型接受更长输入且不报错，是否已证明长距离推理可靠？

**逐步解析与验收：** 没有。将关键证据放到不同位置并加入干扰，固定问题和解码协议，测量正确率随长度与距离变化；同时报告缓存、延迟和内存。验收区分能输入、能计算、能有效使用三层，不用支持的最大长度代替任务能力证据。
